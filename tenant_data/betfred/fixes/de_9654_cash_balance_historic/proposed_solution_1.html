When to use Solution 1

Yes — finish each year to gold before the next. Loop: SQL→S3 → arrange → MERGE that year into Redshift → next year. Camera only after all five years. Better resume + safer dim timeout than one 42.7M MERGE.

Alternative: Solution 2 is one extract for the full pre-cutoff window (~42.7M) with num_partitions=1 — simplest ops if BAU allows one multi-hour scan.

Locked write path + year loop

  1. Per year (repeat ×5): SQL→S3 → S3→Iceberg → Iceberg→Redshift MERGE for that year only, then move to the next year. Do not extract all five years first and MERGE once.
  2. SQL→S3: EXISTING {env}-sql-server-extraction (off-peak, NOLOCK, PlayerBK, num_partitions=1).

3. MERGE vs UNION — solid proof (Andrew)

Andrew asked whether UNION might replace MERGE. Short answer: use MERGE with a hard date gate. UNION is only safe as a compose of two already-disjoint sets — it is not the Redshift write API we use today.

3.1 What the platform actually does today

LayerMechanismEvidence
BAU camera gold redshift_sync → Redshift MERGE … WHEN MATCHED UPDATE … WHEN NOT MATCHED INSERT on player_bk, balance_date uk_digital_dimension_cash_balance.py; etl-common redshift_sync.py
Migration Iceberg insert_pattern: upsert_nocheck → Iceberg MERGE self_exclusion.json; etl-common iceberg_sync.py
Sibling historic gold seed Dim is_initial_load reads *_legacy Iceberg, date filter, then redshift_sync MERGE — then normal CDC path uk_digital_dimension_self_exclusion.py (date_last_modified < 2026-04-01)
Spark unionByName in cash_balance Only updates in-memory baseline between days — not historic SQL ∪ CDC into gold update_baseline in the cash_balance dim

EXAMPLE — self_exclusion pattern (what we copy)

# self_exclusion.py (concept)
if watermark == 1970-01-01:          # is_initial_load
    load FROM dimension_self_exclusion_legacy
    WHERE date_last_modified < '2026-04-01'
    → redshift_sync MERGE
# then normal CDC / curated path for later rows

# cash_balance tip (same idea)
if watermark == 1970-01-01:
    load FROM dimension_cash_balance_legacy
    WHERE balance_date < '{CUTOFF}'
    → redshift_sync MERGE on (player_bk, balance_date)
# then camera from player_balances for days ≥ CUTOFF

3.2 What goes wrong with blind UNION

If you…Then…
UNION ALL legacy + camera into gold with overlapping (player_bk, balance_date) Duplicate keys — reporting double-counts
UNION curated Iceberg dimension_cash_balance_legacy with player_balances Different grain (mart change rows vs 6.58B audit CDC) — invalid table
MERGE without date gate across Jun–Jul 2025 overlap Silent overwrite — SQL load-stamp vs camera event-day fight on same PK

EXAMPLE — colliding key (why blind UNION fails)

Same business key on both sides of the cutoff fight:

  legacy row:  player_bk=P1, balance_date=2025-06-20, balance=10.00  (SQL mart)
  camera row:  player_bk=P1, balance_date=2025-06-20, balance=12.50  (CDC day)

Blind UNION ALL → TWO gold rows for (P1, 2025-06-20) → double-count.
Blind MERGE with no date gate → last writer wins silently (wrong semantics).

Safe: legacy only where balance_date < cutoff;
      camera only where balance_date ≥ cutoff;
      then MERGE each set (or compose then MERGE — see 3.3).

3.3 When UNION is OK

Only as Spark compose after proving disjointness:

EXAMPLE — safe compose (UNION then still MERGE)

legacy  = Iceberg legacy WHERE balance_date <  cutoff
camera  = CDC transform     WHERE balance_date >= cutoff
assert  count(legacy ∩ camera on PK) == 0
frame   = legacy UNION ALL camera     -- compose only
write   = redshift_sync MERGE(frame)  -- still MERGE to gold

# That is still the self_exclusion idea (gate then write).
# It is NOT “replace MERGE with UNION.”
Recommendation to Andrew: lift-and-shift = extract SQL → Iceberg legacy (upsert_nocheck) → date-gated MERGE into dimension.cash_balance → camera for ≥ cutoff. Same as self_exclusion. Do not UNION CDC audit into the mart legacy table.

Volumes (test Unity, 2026-09-09): SQL total 103,767,561; pre-Jul 42,706,989; pre-16 Jun 41,539,433. Table is a HEAP (~2.7 GB, no indexes). Yearly extract ≈ 5 Glue runs (peak year ~2024 ≈ 20.7M rows; peak month 3,188,671).

Write path: year-by-year to Redshift — for each year finish SQL→S3 → S3→Iceberg → Iceberg→Redshift (MERGE that year slice only), then the next year. Camera only after all five years.

Jobs / artefacts per hop (researched):

  • SQL→S3: EXISTING sql-server-extraction (dev / prod verified). Lands yearly parquet under s3://raw-dp-{env}-…/sql-server-extraction/CashBalance/segment=<year>/ (CashBalance prefix not created yet — expected before first run).

Sibling legacy table dimension_self_exclusion_legacy already exists in DEV and prod.
  • Iceberg→Redshift: EXISTING uk_digital_dimension_cash_balance + NEW initial_load tip (self_exclusion pattern) — MERGE year slice only where balance_date < cutoff. Dim timeout today 120 min.
  • Camera (after all years): same dim job BAU path from player_balances for ≥ cutoff (DE-9554 path).

SQL extract guardrails (mandatory): partition_column=BalanceDate; partition_column_type=date; num_partitions=1 (mandatory baseline for HEAP); fetch_size=100000; serial execution only (no parallel year slices); NOLOCK for historic read. Missing/mis-set partition config can cause date fan-out and HEAP stress.
